# 턴 주기 함수 전수 (리프트 실행 기록)

> 공개본 안내: `notes.tsv`·`notes_auto.tsv`는 공개본에 없다(공개 저장소는 .tsv 파일을 받지 않는다). 두 표의 내용은 아래 분류별 쪽에 합쳐 있다.

> **이 문서에서 찾는 법**: 함수 하나는 분류 쪽에서 RVA로 찾는다. 최적화 후보는 아래 「자체 비용 상위」, 흐름별 시간은 「포함 비용 상위」. 해석을 더할 때는 `notes.tsv`에 한 줄을 쓰고 `python -X utf8 tools/materials/cycle_pages.py`를 돌린다. 분류 쪽과 이 문서의 「현황」 아래는 생성 결과이므로 직접 고치지 않는다(이 머리말은 `README.head.md`).

## 1. 무엇을 기록했나

- 범위: 10일 플레이어 턴 → 컴퓨터 군단 전략 → 10일 진행 → 20일 턴 진입까지 한 주기에서 실행된 **모든 함수**(게임 함수, UI, 엔진, CRT 포함). 기계 번역본(리프트, `recon/lift`)으로 같은 세이브를 처음부터 끝까지 돌려 얻었다. 리프트 결과는 원작 기록 판과 난수 9,518회·최종 메모리(다른 바이트 9개)까지 같다(`recon/lift/PLAN.md` 6절).
- 사용자 지시(2026-11-27): 대도서관에는 리프트 안에서 도는 함수 전체를 기록한다. 게임 최적화도 이 기록을 보고 하므로 함수별 호출 수와 비용을 남긴다. 읽기 좋은 C++ 복원은 규칙 함수만.
- 측정 근거는 세이브 한 판(10일 스냅숏, 16세력)이다. 이 판에서 들어가지 않은 함수는 표에 없다. 호출 수·비용은 이 판의 값이다.

### 1.1 리프트가 돌리지 않는 것 (최적화에서 「전체」의 범위)

이 기록은 게임 상태기계(프레임 함수 `573040`과 그 작업 스레드)가 도는 부분이다. 다음은 들어 있지 않거나 비용이 0에 가깝게 잡힌다. 실제 게임 프레임 시간에는 이것들이 더해진다.

- **그리기·소리·입력**: 렌더 스레드, GPU, 소리, 입력 처리는 돌리지 않는다. 스냅숏 이전부터 있던 스레드도 돌지 않는다(그 스레드를 기다리는 폴링은 멈춤 검사로 잡는다).
- **건너뛴 호출**(`tools/materials/emu/m2_run.py`의 `SKIP`·`SKIP_AT`, 2026-11-27 전체 실행에서 건너뛴 횟수): 레이아웃 읽기 `870470` 108회, 위젯 애니메이션 재생 `871270` 95회, 얼굴 노드 `85AE70` 72회, 지도 표지 찾기 `19F080`(`1B4030` 안) 69회, 말풍선 글자·등장 `1BA6A0` 39회, 말풍선 퇴장 `874890` 30회, 부대 표지 추가 `1B00D0` 28회, 그 밖의 UI 위젯 설정 20여 곳 각 1~8회, Steam 업적 `3F02E0` 1회. 저장(`3FA2A0`·`3F3540`·`3EDE50`)은 0회. 건너뛴 함수와 그 아래 함수는 표에 없다.
- **운영체제 호출**: 아래 가져오기 함수는 리프트 안의 대체 함수로 처리하므로 비용이 거의 0이다(원작에서는 커널·잠금 비용이 있다). `EnterCriticalSection`·`LeaveCriticalSection`, SRW 잠금, `Heap*`, `Fls*`·`Tls*`, 이벤트(`CreateEvent*`·`SetEvent`·`ResetEvent`·`WaitFor*`), 조건 변수, `Sleep`·`SwitchToThread`, `QueryPerformanceCounter`·`GetSystemTime*`, `MultiByteToWideChar`·`WideCharToMultiByte`, `_beginthreadex`(작업 스레드 `93BB90`만), 창·커서 함수 몇 개.

## 2. 열의 뜻

| 열 | 뜻 |
|---|---|
| 단계 | 전략 = 10일 턴에서 진행 시작 전(프레임 245 이전), 진행 = 그 뒤, 전략+진행 = 둘 다 |
| 호출 | 이 주기에서 불린 횟수(모든 스레드) |
| 자체 % / 포함 % | 리프트 실행 시간(TSC) 중 이 함수 자신 / 하위 함수까지 쓴 몫. 다른 스레드가 도는 동안(작업 스레드가 프레임을 넘어 기다리는 시간 포함)과 프로파일러 자체 시간은 뺀다. 재귀 함수는 포함 %에서 다시 센다. **리프트 기준 상대값**이다: 원작 기계어 시간과 비율이 다를 수 있다(리프트의 호출·메모리 접근 비용이 더 크다). |
| 부름 | 이 함수가 다른 함수를 부른 횟수. 작은 함수를 아주 많이 부르는 함수는 자체 %에 리프트의 호출 비용이 섞인다 |
| 주요 호출자 | 호출 수 상위 3곳(`호출자:횟수`, `-` = 실행 시작점) |
| this · 필드 | 처음 16번 호출의 `[RCX]` vtable RTTI 클래스와, 그 호출들이 RCX 기준으로 읽은(r) / 쓴(w) 오프셋. 클래스가 [구조체](../structs.md)에 있으면 필드 이름. **어림값**: 인수 없는 함수도 그때 RCX에 있던 객체 클래스가 찍힌다(`11040` 예). 주소는 아래쪽 가장 가까운 포인터 인수 기준이라, 이웃 객체 읽기가 큰 오프셋으로 보이기도 한다 |
| 분류 근거 | 첫 분류 규칙(`tools/materials/cycle_functions.py`): CRT 주소, 판단표 노드 실행 함수·노드 클래스, 엔진(`kids::`) 클래스, UI 클래스·문자열, 게임 데이터 클래스, `State` 클래스, 기반(호출자 40곳 이상·전역 없음·256바이트 미만). `(호출자)` = 호출의 80% 이상이 UI·엔진·AI 함수에서 온다. 해석 순서용이며 사실이 아니다 |

## 3. 해석 층 (`notes.tsv`)

열: `rva, name, role, args, ret, reads, writes, calls, conf, src, date`.

- `reads` / `writes`: `this.force(+0x10)`, `world.corps_table(+0xE0D0)`, `person.status(+0xE6)`, `G:142780F60(world)` 꼴로 `;`로 나눈다. 측정 열(`prof_access`)과 스크립트로 맞춰 볼 수 있게 쓴다.
- `calls`: 뜻이 있는 하위 호출만(`331780 생존 판정` 꼴).
- `conf`: 확정(코드 + 실행 기록 일치) / 코드(디컴파일 판독) / 추정.
- 근거 순서: `docs/orig` → `AI_TacticsMod/tools/decomp_cache.py get` → 기드라 → 리프트 실행 기록(`recon/build/m2/prof_*.tsv`).
- 점검: `python -X utf8 tools/materials/cycle_check.py [RVA …]`가 `calls`의 RVA를 실행의 피호출자와, `this.`·`G:` 항목을 처음 16번 호출의 메모리 접근과 맞춰 본다. 「not seen」은 이 판에서 그 분기를 타지 않았다는 뜻일 수 있다(시범 15줄 중 4줄이 그렇다: `11040` 첫 생성, `231C50` param_2, `1AE710` 새 세력 화면, `2B6490` 군사 사망). 분기 논리 자체는 이 점검으로 알 수 없다. 논리는 읽기 좋은 C++가 리프트 교체 표로 채점될 때만 확인된다(`recon/lift/PLAN.md` 7절).

## 4. 대량 해석 층 (`notes_auto.tsv`)

열: `rva, name, role, conf, src`. 쪽에서는 *기울인 이름*으로 보인다. `notes.tsv`와 대도서관 함수 지도에 역할이 있으면 그쪽이 먼저다.

- `src` = `A-패턴:<종류>`: `tools/materials/cycle_auto.py`가 디컴파일 모양(빈 함수, 상수 반환, 필드 getter·setter, 전역 읽기, 소멸자·생성자, 감싼 호출 등)으로 쓴 줄. `A-같은본문`: 본문이 같은 함수의 해석을 옮긴 줄(묶음은 `materials/cycle_dupes.tsv`). `A-기호`: 기드라 기호 이름(CRT·라이브러리).
- 작업자 묶음: `tools/materials/cycle_batch.py`가 함수마다 측정 사실과 디컴파일을 한 파일로 묶고(`recon/build/cycle_batches/`, 저장소 밖), 작업자가 `rva, name, role, conf`를 쓴다. 들어온 줄은 표본으로 검토한다. 오답률은 보정 묶음(답을 아는 함수를 가리고 섞음)으로 잰다.
- `conf`: 코드(디컴파일에서 그대로 읽힘) / 추정. 이 층에는 「확정」이 없다.
- 믿을 만한 정도(2026-11-27 보정 묶음, 답을 아는 함수 71개, `materials/cycle_calib/`): 작업자 줄은 맞음 75%, 부분(동작은 맞고 게임 뜻이 빠지거나 세부 하나가 틀림) 18%, 오답 7%(95% 구간 3~15%). 오답은 모두 `conf` = 추정 줄에서 나왔다. 미분류 함수는 11개 중 2개가 오답이었고, UI와 1KB 이상 함수는 아직 재지 못했다. 추정 줄의 게임 뜻은 디컴파일로 확인한 뒤 쓴다. A-패턴 줄은 표본 36줄의 동작이 모두 맞았다.
- B층 진행(2026-11-27, Sonnet 일꾼 5병렬): 일꾼 묶음 52개, 파 1~17. 마지막 2개(상태 관리자 프레임 갱신 `573040`, 그 아래 `67D8A0`)는 지휘 세션이 직접 썼다. 이로써 리프트가 돈 3,937개 모두에 이름과 한 줄 역할이 있다. 파는 아래에서 위로 간다(`tools/materials/cycle_plan.py next`: 남은 피호출자가 모두 이름을 얻은 함수, 호출 고리는 한 덩어리). 그래서 앞 파의 이름이 뒤 파의 근거가 된다. 기드라가 함수로 잡지 않은 220개(디컴파일 없음, 크기 미상)는 리프트 생성 코드의 명령 주석(`recon/lift/gen/lift_NNN.cpp`의 `L_<주소>:; // <명령>`, `cycle_lib.lift_asm`)을 어셈블리로 보여 주고 읽혔다. 가운데값 4명령, 최대 42명령이다.
- 교차 확인: 파마다 병합한 줄의 15%를 둘째 일꾼이 첫 답을 가린 채 다시 쓰고, 두 답이 다른 줄만 지휘 세션이 판정했다(`cycle_plan.py xcheck`, `cycle_grade.py --vs`; 뜻이 갈리는 줄은 디컴파일을 열어 확인, 표현만 다른 줄은 두 답만 보고 판정). x1 153줄 오답 3(2.0%), x2 84줄 오답 6(7.1%, 모두 추정), x3 68줄 0(부분 1), x4 39줄 0(부분 3), x5 26줄 0, x6 21줄 0(부분 1), x7 24줄 0(부분 2), x8 11줄 0, x9 9줄 0, xA(10~13파 15줄 + 디컴파일 없는 함수 33줄) 48줄 0(부분 1), xB(14~17파) 11줄 0. 합계 494줄, 오답 9(1.8%). **한계**: 두 일꾼이 같은 입력(같은 잘린 디컴파일, 같은 틀린 하위 함수 이름)을 보면 같은 실수를 한다. 그래서 이 비율은 아래 재검토가 잡은 객체 혼동을 거의 잡지 못했다.
- 재검토(`cycle_batch.py --review`, 일꾼이 현재 해석을 디컴파일과 대조, `cycle_grade.py --changed` → 지휘 세션 검토 → `--fix`): 1~2파는 묶음에 world 표 이름 줄이 없었고, 틀린 하위 함수 이름(예: `32E3B0` = 거점 객체를 세력으로)을 근거로 썼다. r1 = 1~2파에서 world 필드를 읽는 줄 280개 → 71개(25%) 고침. r2 = 고친 줄을 부르는 함수 195개 → 70개. r3 = 그다음 호출자 49개 → 21개, 지휘 세션이 손으로 7개(거점 vtable+0x90 = 금). r4 = 8개 → 2개. 고친 줄은 `src` = `B-검토:<묶음>`(지금 190줄, 교차 확인과 지휘 세션이 쓴 줄 포함). 재검토는 호출 관계를 따라가므로 필드·상수를 직접 읽는 줄은 잡지 못한다. 그래서 확정 사실의 틀린 표현(군단장 = +0xCA/+0xCC, 이민족 = 0x34~0x3D, 소재 = +0xE2, 군주 위치 = `234020`, 경관/명승, 징병/모병 등)을 문자열로 전수 점검해 5줄을 더 고쳤다(`B-검토:c19`). 디컴파일 없는 함수의 표 항목 크기는 어셈블리의 곱셈 역수 상수로 다시 계산했다: 14줄 중 1줄(`235470`, 0x9A → 0x98)이 틀렸다. 리프트 명령 목록에 꼬리 점프 대상의 몸체가 붙은 함수가 1개(`B19FF0` + `ACB320`) 있다. 주된 오류: 세력·군단·거점·지역·건물 혼동(`B7170`·`22D3C0`·`40C20`은 군단을 돌려준다), 금·군량·병력 혼동(거점 vtable+0x90 / +0xA0 / +0x3C), 도시 수와 거점 수 혼동(`22C410`·`225C50`은 도시 52칸만 돈다), 거점 담당 칸(+0xCA 모병, +0xCC 훈련)을 군단장으로 읽음.
- 남은 위험과 C층: 대량 층 일꾼 줄 3,297개 중 「추정」이 약 55%다. 디컴파일이 150줄을 넘는 함수는 일꾼이 앞 150줄만 봤다(249개). C층(손으로 깊이 읽기, `recon/lift/PLAN.md` 8절: 판단표 폐포 + 자체 비용 상위) 후보는 `materials/cycle_tierc.tsv`(`cycle_plan.py tierc`)에 모은다: 786개, 태그는 판단표 노드 172 · 판단표 하위 378 · 잘림 249 · 자체 비용 상위 40 · 포함 비용 상위 40(겹침 있음). 상태 관리자 `573040`도 잘린 채 훑어 쓴 줄이라 이 목록에 있다.
- C층 결과(2026-11-27): 후보 786개 모두 `notes.tsv`에 있다. 묶음 31개마다 Sonnet 작업자가 디컴파일 전체를 읽어 쓰고(인수·반환·읽기·쓰기·호출·규칙 여부), 둘째 작업자가 같은 입력으로 다시 확인했다. 출처 표시: `C-작업자` 668개(둘째 작업자가 고칠 곳 없음), `C-검증` 112개(둘째 작업자가 고침, 사람이 읽지 않음), `C-검토` 6개(지휘 세션이 디컴파일 줄을 읽음). 규칙 함수(자기 본문에 상수 비교·식·선택 순서·난수가 있는 것) 241개는 `materials/cycle_rules.tsv`에 있다. 두 작업자가 같은 실수를 하면 이 확인으로는 잡히지 않는다(B층 재검토 경험).
