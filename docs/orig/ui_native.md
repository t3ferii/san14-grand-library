## 1. 개요

* 원작 UI는 화면 자료(`0002/ScreenLayout.rdb`의 LCSK 레이아웃)가 위치·크기를 정하고, 컨트롤 객체가 자기 스타일 부품으로 그린다. 화면 클래스는 `C…State`(RTTI)이며 생성 시 레이아웃 이름 문자열을 쓴다. (UI_ADD_GUIDE.md:9-23, 48-53)
* 정적 UI 지도(2026-10-18, 옛 빌드 분석본 + 설치 ScreenLayout): 전체 RTTI 9,697개 중 UI 후보 3,531개, 설치 LCSK 레이아웃 1,085개, 부품 45,444개, ScreenLayout 인덱스 18,046항목, 한국어 메시지 22,525개. 후보 분류·슬롯·리소스 이름만으로 실제 클릭 경로·ABI가 입증되지는 않는다. (UI_ATLAS.md, research/ui_atlas/README.md:25-51)
* 조회 도구: `python -X utf8 AI_TacticsMod/research/ui_atlas/atlas.py search|bundle|class|function|layout|message|coverage` (README.md:5-24). 전체 JSONL/SQLite를 통째로 읽지 않는다.
* 실제 화면에서 보고 눌렸다는 성공 사례만 정답으로 취급한다(반란 하단 바 2026-10-23, 숙련 설정2 소·중·대 2026-10-25). "생성됨·등록됨·클릭됨"은 화면 출력의 증거가 아니다. (UI_ADD_GUIDE.md:3-5, 46)

### 1.1 화면 상태와 컨트롤 객체의 수명

`C…State`는 화면의 상태 전이를 진행한다. `CUILayout` 계열은 레이아웃 리소스와 자식 객체를 보유한다. `CDialog`와 `CCmnButton`도 이 계열이다. 상태 하나가 레이아웃 여러 개를 가질 수 있고, 레이아웃의 리소스 노드마다 런타임 컨트롤을 연결할 수 있다.

| 단계 | 현재판 경로 | 확인한 동작 |
|---|---|---|
| 상태 진입 | 예: `CStrategyDiplomacyState` vtable `1441B70`, 슬롯 1 `72B420` | 명령 종류 `state+0x470`에 맞는 창을 생성해 `+0x480`에 보관한다. 창의 vt+0x1A0에 `+0x478` 데이터와 종류를 넘겨 구성한 뒤 vt+0x38을 부른다. |
| 레이아웃 로드 | `CUILayout` vtable `1345530`, 슬롯 38 `86E920` | 논리 이름으로 리소스 작업을 찾아 `layout+0x90/+0x98`에 보관(2.1절). |
| 초기화 | 슬롯 40(vt+0x140) 기본 `8706D0` | `8704F0`으로 트리를 준비하고 `92D550(layout+0x130,layout)`으로 노드 표를 만든다. 파생 클래스는 슬롯을 바꿀 수 있다. `CArmyButtonMenu`는 `8704F0` 직접. |
| 등록 | vt+0x38 `869210 → 869120` | 컨트롤 표를 준비하고 UI 관리자(`010F20`)에 레이아웃을 넣는다. 관리 목록 선택은 `layout+0x14` 층 번호를 쓴다. |
| 입력·갱신 | `874140` 관리 목록 순회, `86CCF0` 이벤트 전달 | 표시 조건과 부모 상태를 확인하고, 객체에 등록한 이벤트 번호로 콜백을 부른다(3.1절). |
| 등록 해제·자식 종료 | vt+0x40 `86BBD0` | `86B600`이 관리 목록에서 객체를 제거한다. `92E660`은 컨트롤 표 `+0x28`과 자식 목록 3개의 객체에 vt+0x40을 호출한다. |
| 상태 종료·소멸 | 외교 상태 슬롯 2 `721110` | 창의 vt+0x40, vt+0x28, vtable 첫 소멸 슬롯 순으로 부르고 `state+0x480`을 지운다. |

`uiclass`에서 화면 타입을 찾고 `uislot`으로 상태·레이아웃의 실제 슬롯을 읽는다. `callers`에서 안 보인다고 호출이 없는 것은 아니다. 하단 바 콜백 `862870`은 함수 추출본 대신 vtable `1470930`과 PE 명령에서 확인했다. 옛 UI atlas의 노드·문자열은 후보를 찾는 데 쓰고, 아래 현재판 주소는 RTTI·직접 CALL·PE로 확인했다.

## 2. 화면 자료 (확정, UI_ADD_GUIDE.md:48-53, 65-87)

* **ScreenLayout.rdb**: 레이아웃 1,085개(8개 버전의 레코드 경계·이름표 확인, 1,082개는 부모 인덱스와 기록된 자식 수가 일치). 나머지 3개도 부모 인덱스를 읽을 수 있으며 각각 한 노드의 자식 수가 집계보다 1개 많다(2.3절). 인덱스 마지막 항목 `0x8C759C7F`는 로케이터 없는 불투명 항목으로 레이아웃이 아니다. (ui_atlas/README.md:60-62)
* **KTID**: 레이아웃 식별자. 게임은 논리 이름을 `common setting`으로 변환한다(2.1절). 하단 바 `cmn_footer_re_cn`의 최종 KTID `0xD8913AB2`는 `origlib.rdb`에서 설치 `ScreenLayout` 형식 `0x5599AA51` 및 본문 머리 `LCSK9500`을 확인했다. 동일한 노드 구성을 가진 자산 변형이 있으므로 노드 패턴은 후보를 좁히는 데 쓴다.
* **LCSK 머리**: `+0x08` 전체 크기. 기존의 `+20`, `+22`, `+24` 등은 **10진수 오프셋**이다. 설치본 전수 대조에서는 `+0x14`의 u16이 1,085개 중 1,045개에서 노드 수와 일치하지만, 구형 4500 39개와 8400 1개는 일치하지 않는다. 따라서 모든 버전에 `+0x14`를 노드 수로 일반화하면 안 된다(2.3절). 예전 `+20/+22`를 16진수로 오독해 `+0x20/+0x22`를 읽으면 엉뚱한 필드를 읽는다. 같은 이유로 기존의 `+24/+26/+28/+30`도 각각 `+0x18/+0x1A/+0x1C/+0x1E`다. 블록 순서(예 `0,1,3,4,5,9,2`)는 정렬하면 안 된다. 736바이트 그림 노드를 복사하면 k1의 표4·표5(9분할 슬롯, 표4 항목 +6은 자기 슬롯 번호)에 슬롯 9칸을 새 번호로 추가한다.
* **노드**: 88바이트(0x58) `Preset_*` 빈 노드는 위치·크기만 정한다(이웃 노드 복사 후 `+0/+2` id, `+8` x(float), 부모 `+54` 자식 수 +1). Preset 노드의 참조는 노드 인덱스로 이루어진다. 일부 동적 버튼의 그림을 별도 스타일로 만든다는 관찰을 LCSK 하위 노드 전체의 그리기 규칙으로 일반화할 수 없다.
* **k1 이름표(kind 1)**: total(+4), nsize(+8), xsize(+12), count(+18 u16), +24 = hsize+nsize. 머리의 십진 +8·+20·+24(0x58 레코드 수), 0x90 이미지 노드면 +26이라는 기존 설명은 버전별 차이에 주의한다(2.3절).
* **엔트리 형식**: `idrk_entry` = 16KB zlib 조각 + 0 조각 + CRC. 원본 인덱스 엔트리는 패치 전 백업 기준(이미 모드 bank를 가리키는 현재 자료를 원본으로 채택하지 않는다).
* 빌드 의존: 레이아웃 자료는 빌드와 무관. 새 빌드 1a4a447d에서는 **traits9(개성 5→9칸) 레코드 4개를 적용하지 않는다**(EXE TimeDateStamp 표, `expected_disabled.json`). (UI_RESOURCE_LIFECYCLE.md:14-18)
* 무장 기본 화면은 원본 부품 125개이고 설치 자산은 bank31 레이아웃 4개(노드 125~128)를 포함해 129개다(외부 모드 확장). (ui_atlas/README.md:62)

### 2.1 이름 → KTID → 레이아웃 노드

1. 현재판 `86E920(layout, x, y, parent, name, …, async)`은 부모를 `layout+0x08`에 저장한다(`876940`). 이름 해시는 초기 hash=0, power=1이고, 바이트마다 먼저 power×=31, 다음 hash+=power×signed_byte를 수행한다. ASCII 이름의 식은 `Σ name[i] × 31^(i+1) mod 2^32`다.
2. 리소스 관리자는 `14DAE0()` 결과의 `+0x210`이다. `14CBA0`이 `common setting`의 등록 키 `0x61AD16CF`로 핸들을 얻는다. `BD0BC0(payload,hash)`는 `payload+0x18` 개수만큼 `+0x90 → u32[]` 키를 순회하고 첫 일치 위치의 `+0xA0 → u32[]` 레이아웃 래퍼 객체 ID를 반환한다. 0이면 기본 래퍼 `0x4688C866`을 쓴다. 관리자 `+0x1D8`의 등록 트리는 `B3CDA0`이 조회한다. `3FF5C0`과 공용 버튼 로더 `8A9140`도 이 등록 키를 쓴다.
3. `B3BB50` 작업 핸들은 `layout+0x90`, 핸들 `+0x20`의 리소스 포인터는 `layout+0x98`에 저장한다. 동기는 `14CF0` 완료까지 `Sleep(0)`으로 기다리고, 비동기는 `401130`으로 보내고 반환한다. `layout+0x124/+0x128`에 좌표를 쓰고 `+0x12C`를 켠다. 동기는 vt+0x140을 호출한다. 이미 `+0x12C`가 켜진 상태에서 다시 동기 호출하면 초기화 슬롯으로 바로 간다.
4. `8704F0`은 리소스 트리의 기준 노드를 `layout+0xA0`에 캐시하고 노드 `+0xF0/+0xF2`의 치수를 레이아웃 슬롯에 넘긴다. 준비가 끝나면 `+0x12C`를 0으로 돌린다. `92D550`은 노드 수 <256에서 `layout+0x130`에 노드당 0x30바이트 레코드 표, `+0x138`에 노드 포인터 표, `+0x140`에 개수, `+0x148`에 소유자 포인터를 둔다. 초기 레코드 종류는 2다.

논리 이름의 해시, 최종 KTID, 레이아웃 노드 인덱스, 클릭 값은 각기 다른 필드다.

### 2.2 원본 등록표와 최종 레이아웃 1,085개

`KIDSSystemResource.rdb`의 KTID `6D011726`인 `_DOK0000` 본문 안에 `common setting`이 있다. 설치본에서 객체 오프셋은 `0x1FB0`, 객체 ID는 `61AD16CF`, 클래스는 `DAC911D7`이다. `BCFDF0`은 아래 세 속성 이름과 ID를 직접 등록한다.

| 속성 | ID | DOK 본문 시작 | 1,085개 u32 행의 의미 |
|---|---:|---:|---|
| ScreenLayoutKeyHashArray | `10FA95C2` | `0x2472` | 논리 이름 해시 |
| ScreenLayoutObjectNameHashArray | `B45B5E75` | `0x3566` | 래퍼 객체 ID |
| ScreenLayoutSettingObjectNameHashArray | `1BF404E7` | `0x465A` | 설정 객체 ID |

같은 RDB의 `208BE13A` DOK가 나머지 연결을 담는다. 설정 객체(클래스 `A1A84F2C`, 속성 `91CE400E`)가 래퍼를 가리키고, 래퍼(클래스 `63336873`, 속성 `15BE61AD`)가 최종 `ScreenLayout.rdb`의 LCSK KTID를 가리킨다. 직접 래퍼 열과 설정을 거친 래퍼가 1,085행 전부 일치하고, 최종 KTID 집합은 설치본의 LCSK 1,085개와 일치한다. 기본 래퍼 `4688C866`의 최종 KTID는 `B126AEA2`다. 대조 대상은 설치 자산의 현재 구성이다.

| EXE의 논리 이름 | 해시 | 래퍼 | 최종 LCSK KTID |

| `02_00_title_pk_cn` | `A2FA1C5A` | `9D2B6822` | `E7A28866` |

`origlib.rdb.read_layout_registry()`는 설치 자료를 직접 읽고 두 연결과 최종 KTID를 대조한다. San14Sim에서 `python -B -X utf8 -m origlib layout cmn_footer_re_cn`으로 한 항목, 이름을 생략하면 해시·래퍼·설정·최종 KTID 순으로 전수 조회한다. [전수 레이아웃 색인](ui_layouts.json)은 설치본 1,085행의 해시와 최종 KTID를 담는다. 이름 해시가 일치하는 원문 문자열은 PE에서 657행(문자열·RVA), ScreenLayout LCSK 본문에서 29행(문자열·출처 KTID·본문 오프셋)을 확인했다. 언어 접미사를 바꿔 같은 해시를 얻은 26행과 기존 원문 이름의 두 자리 숫자 한 곳을 바꿔 같은 해시를 얻은 15행은 각각 추정 후보로 표시했다. 숫자 후보는 중립·한국어 분류만 포함하며 각 행에 원문 출처 이름을 함께 기록한다. 해시 일치는 원문 존재나 사용의 증거가 아니다. 남은 358행은 이름 후보 없이 해시와 KTID로 조회한다. 화면에서의 실제 호출 경로는 상태별 코드에서 확인한다.

### 2.3 부모 인덱스와 자식 수의 검증

일반 레코드의 부모 인덱스는 `+0x32 u16`이며 루트는 `0xFFFF`다. 저장된 직계 자식 수는 `+0x36 u16`이다. 기존 atlas에서 두 값의 대조가 빠졌던 4개를 설치본 LCSK 본문에서 다시 확인했다.

| 최종 KTID | 노드 수 | 자식 수 대조 |
|---|---:|---|
| `07E32B09`(8400) | 5 | 구형 레코드의 부모 `+0x2E`, 자식 수 `+0x34`. 부모 값 `[-1,0,1,0,0]`과 자식 수 `[3,1,0,0,0]` 일치 |
| `4FEB10A8`(8500) | 49 | 21번 `Null_list`의 자식 수는 21, 해당 부모를 참조하는 노드는 20개 |
| `AC3BBAC4`(8500) | 31 | 0번 `Root`의 자식 수는 14, 해당 부모를 참조하는 노드는 13개 |
| `EC3FB638`(8500) | 33 | 12번 `Null_list_area`의 자식 수는 21, 해당 부모를 참조하는 노드는 20개 |

세 8500 파일의 부모 인덱스는 루트 표지 또는 그 노드보다 앞선 인덱스다. 런타임 로더가 자식 수 차이를 처리하는 경로는 미확인이다.

추가 대조: `4FEB10A8`에는 루트 표지 `0xFFFF`가 노드 0과 48에 두 번 나온다. 48번은 자식 수 0인 `Preset` 노드이고, 바로 앞 44~47번은 21번 `Null_list`를 부모로 둔 같은 이름 계열이다. `AC3BBAC4`와 `EC3FB638`은 루트 표지가 각각 노드 0 하나뿐이다. 이는 설치 자산의 기록을 관찰한 것이며, 48번을 21번의 자식으로 고치거나 누락된 자식을 하나 찾아냈다고 판정하는 근거는 아니다. 세 자산 모두 `origlib.rdb`로 본문을 읽고 기존 `ui_atlas/build_layouts.py`의 레코드 경계·부모 필드 해석으로 다시 대조했다.

**머리 노드 수의 버전 차이와 읽기 주의(설치본 1,085개 전수).** 위 세 8500 자산의 섹션 1 노드 수는 49·31·33이고 각각 머리 `+0x14` u16과 같다. `D8913AB2`의 9500도 25로 일치한다. 반면 8400 `07E32B09`는 섹션 1에 5개인데 `+0x14`는 2이고, 4500 `0CF6FDA2`는 26개인데 `+0x14`는 12다. 기준 노드 수는 기존 `parse_layout`이 섹션 1의 `+0x12` u16을 읽은 뒤 레코드 경계와 이름표 개수를 대조한 값이다. 1,045개가 머리 `+0x14`와 같고 40개(4500 39개·8400 1개)가 다르다. 수정 전 `origlib.rdb.parse_lcsk_head()`의 `nodes`가 읽던 `+0x20`은 위 네 8500/9500 예에서 전부 0이며 설치본 1,085개 중 1,083개가 섹션 1 노드 수와 다르다. 나머지 2개의 우연한 일치도 이 필드의 의미를 입증하지 않는다. 읽기 함수를 섹션 1의 `+0x12`를 사용하도록 수정했다. 이는 설치된 자산에 대한 정적 대조다.

자료 로딩 단계의 범위: `101130`은 자료 종류 `5599AA51`에 `F49AB0`이 만든 객체를 등록하고, 그 객체의 vtable `1700EB0` 슬롯 11은 `F50530`이다. `F50530`은 입력에서 먼저 `0x4C`바이트를 읽고 헤더의 전체 크기에 맞게 메모리를 할당한 뒤 나머지 본문을 이어 읽는다. 해당 함수에는 부모 인덱스나 자식 수를 검사·수정하는 분기가 없다. 이는 원본 바이트를 전달하는 이 로딩 단계에 한정되며, 이후 다른 런타임 트리 구성 코드가 불일치를 어떻게 처리하는지는 여전히 미확인이다.

* 표시와 alpha는 별개: 클릭 가능이 그리기 성공의 증거가 아니다. 표시 비트·부모 표시 캐시(`873370` 무효화)·자기 alpha(`873450`)·부모 alpha를 함께 본다. 원작 타이틀 메뉴 8행은 alpha 애니메이션을 가지며 추가 행에는 없다. (UI_FAILURES_AND_RECIPES.md:25-35)

### 3.1 현재판 컨트롤 생성과 이벤트

- `9309C0(table,index,style,kind,group,order)`는 index 범위와 노드 포인터부터 검사한다. 위치(`92F1B0)), 노드 `+0xF0` 치수와 `+0xF4/+0xF8` 배율을 구해 새 버튼 vt+0x188에 전달한다. `92E7C0`으로 원 노드를 처리하고 `930740`으로 그룹 0..2의 목록에 등록한다. 목록의 비교 키는 등록 레코드 `+4`의 order이며, 노드 레코드 종류는 4로 바뀐다.
- `1A4FB0(control,event,functor)`은 콜백을 복제해 `869690(control+0x70,event,…)`에 등록한다. `86CCF0`은 같은 번호의 첫 항목을 찾아 페이로드를 functor vt+0x10(슬롯 2)에 넘긴다. 버튼 `+0x80`의 값은 이벤트 번호와 별개다.
- `876580`은 객체 `+0x40` bit0을 바꾼다. `(flags&3)==3` 진릿값이 바뀌면 `+0x10=-1`과 자식 캐시를 무효화한다(`875720`). `871600`은 하위 두 비트와 부모 조건을 확인한다. `931DA0(table,index,visible)`은 `931E20`으로 리소스 노드 표시를 갱신하고 런타임 컨트롤이 있으면 그 객체의 vt+0xC8도 호출한다.
- 입력 순회 `874140`도 `flags&3`과 부모 표시 캐시를 검사한다. 처리 후 `+0x40` bit5가 켜지면 UI 관리자 `+0x180`에 처리 표시를 쓰고 순회를 끝낸다. `8734E0`은 bit7을 켜고 `0x7FFFFFFB`를 전달한다.

### 4.3 공통창·목록·확인창 (확정/추정, ui_atlas/README.md:52-59, UI_ADD_GUIDE.md:88-94)

* 무장 선택창 준비 함수 `45D850`(옛 `45B620`)은 `2528E0`으로 기본 설정을 만들고 `253CE0`으로 호출자 설정을 복사한다. 크기 0x2F0의 `CDataSelectDlgBase<CPersonData>`(vtable `13AF608`)을 초기화해 전역 `27D6CF0[종류]`에 저장한다. 설정 `+0x00`은 후보 목록, `+0x18`은 선택 방식(기본 1), `+0x1C`는 선택 상한(기본 INT_MAX), `+0x28`은 제목, `+0x80`은 결과 목록 포인터다.
* 무장 선택창의 준비와 재사용은 서로 다른 단계다. `45D850(config, 종류)`은 `27D6CF0[종류]`에 기존 창이 있으면 그 창의 vt+`0x28`을 부르고 소멸시킨 뒤 포인터를 비운다. 기본 설정 `2528E0`을 만든 다음 `253CE0`으로 전달 설정을 복사하고 새 창의 vt+`0x1F8`로 설정해 같은 칸에 보관한다. 따라서 같은 종류로 준비를 다시 하면 기존 창 객체 자체가 교체된다. `253CE0`은 단순 구조체 전체 메모리 복사가 아니라 함수 객체 복제와 문자열·세 묶음 복사를 별도로 수행한다.
* `45E090`은 `335110`이 0이고 준비된 창과 상태 관리자 항목이 있을 때만 연다. 호출자 설정이 있으면 준비된 창 설정의 `+0x80`을 갱신하고, 설정 `+0x30/+0x38`이 비었는지에 따라 각각 빈 목록 또는 전달 목록으로 갱신한다. 이후 `CDialogOpenStateBase<CDataSelectDlgBase<Data>>`를 등록하고 응답을 기다려 결과를 반환한다. 준비 단계에서 설정을 복사하는 것과 열기 단계에서 일부 필드를 다시 넘기는 것은 별개이며, 실패 조건에 걸리면 이 함수는 0을 반환한다.
* 열기 함수 `45E090`(옛 `45BE60`)은 준비된 창에서 결과 목록 포인터 등을 갱신하고, `460F70`(옛 `45ED60`)으로 0x480바이트 상태를 등록한다. 상태 RTTI는 `CDialogOpenStateBase<CDataSelectDlgBase<CPersonData>>`, vtable은 `13F4B60`이다. 관리자 `+0x40`의 대기 큐는 0x10바이트 항목을 쓰고 `+0x30`에 개수, `+0x38`에 용량을 둔다. `573040`이 큐를 소비한다.

- 두 화면 모두 버튼을 도움말 관리자에 연결한다(`89D1B0`). 공통 콜백 `831170`은 버튼 클릭 값 `+0x80`이 0이면 메시지 ID `0x607`, 1이면 `0x606`을 `30F010`으로 읽어 도움말에 전달한다. 한국어 `msgdata_exce` 1번 표는 각각 **빨리 넘기기**, **건너뛰기**다. 이 근거로 두 화면의 왼쪽/오른쪽 버튼을 각각 빨리 넘기기/건너뛰기로 식별할 수 있다. 원본 기록 좌표와 사용자 화면 좌표는 좌표계가 다르므로 직접 동일시하지 않는다.
- `CDuelLayout` 기반과 `CDuelOpeningLayout`·`CDuelTurnLayout`·`CDuelResultLayout`의 vtable은 판정 슬롯 51~54에 같은 주소 `812700/812890/8125F0/8126F0`을 둔다(`uislot` RTTI 표). 하지만 그 슬롯의 실제 구현 본문과 `+0x20` 포인터에 배정되는 구체 객체는 기존 함수 추출본에 없어, 도움말 식별을 곧바로 `808CD0`·`808C90`의 입력 동작과 동일시하지 않는다. 바이트 추출도 DB 검증 오류(`Native CALL bytes differ at RVA5F14DA`)로 실패하여 구현은 미확인이다.

### 4.13 지도 부대 깃발(초상화 깃발)의 생성·제거 (현재 Steam 빌드 `1a4a447d` 디컴파일, 2026-11-24, 실게임 미확인)

- **깃발 클래스와 레이아웃.** 지도 위 부대 깃발(초상화 원·병력 막대)은 `CArmyInfoLayout`(vtable `139BA98`)이다. 초기화 슬롯 63 = `1A0430`이 `870470`으로 레이아웃 `00_81_07_0400_unit_flag`를 읽는다. 생성자는 `19BB20`, 객체 크기는 0x278이다. 깃발의 작은 얼굴은 `19A270`·`19A8B0`·`19B350`에서 `1BA4E0`으로 지정되는 것으로 보인다(호출자 목록, 본문 미판독).
- **`1B4750`은 깃발이 아니다.** `1B4750`은 부대 행동 패널 `00_81_09_unit_action_ot`를 읽는 함수다. 그 안의 `1B4823 CALL 1BA4E0`은 행동 패널의 얼굴 지정이다.
- **깃발 관리자.** `*(11160()+0x20)`이다. `11160`은 정적 객체 `1B94DF0`을 돌려준다(스레드 안전 지역 정적 초기화). 관리자 vtable은 `13A1548`(CArmyInfoLayoutBase)·`13A13B0`이다.
  - **슬롯 41 `+0x148` = `1B00D0(관리자, 부대)` 추가.** `331780(부대)`와 `14DAE0()+0x210 != 0`을 확인한다. 이어 슬롯 42로 그 부대의 옛 깃발을 지운다. 그다음 0x278바이트를 할당하고 `19BB20` → vt`+0x1F8`(깃발, 관리자, 부대) → vt`+0x38`을 거쳐 목록에 넣는다.
  - **슬롯 42 `+0x150` = `1B0B00(관리자, 부대)` 제거.** 목록을 잠금 없이 걷다가 `flag[0x3E]`(= `flag+0x1F0`)가 그 부대인 노드를 찾는다. 그 노드에 vt`+0x40`, vt`+0x28`(깃발, `14DAE0()+0x210`), vt`+0`(깃발, 1)을 부른다. 노드 반납(`189B0`)만 임계 구역 `27D4108`(`27D4100 != 0`일 때) 안에서 한다.
  - **목록.** `관리자+0x98` = 핸들(u32*)이다. 핸들은 풀 `27D4140`의 머리 배열을 가리킨다(`27D4138 != 0`, 핸들 < `27D4170`). 노드는 {깃발, 다음}이다.
  - `14DAE0()+0x210`(`1BA2BC0+0x210`)은 종료 때만 지워지는 앱 핵심 객체다.
- **깃발이 붙는 때(원작 전부).**
  - **등장 `25DA10(부대, 0xBD10)`.** 처음에 부대 `+0x56`(등장 지연 0~9)을 1 줄인다. 0이 아니면 등장하지 않고 0을 돌려준다(깃발 없음). 등장하면 다음 순서로 진행한다.
    1. 칸 `+0x2A`를 정하고 `0xBEC60`/`990C0`/`225830`을 부른다.
    2. `*(11160()+0x20)`이 0이 아니면 슬롯 41로 깃발을 추가한다. 관리자가 0이면 깃발 없이 등장한다.
    3. 같은 관리자에 `1A4F50`을 부르고, 부대 `+0x26 |= 0x42`를 한다.
    4. 마지막으로 `243610(칸, 22F4A0(부대))`이 칸 `+0x1C`에 부대 번호를 쓴다.
  - **25DA10의 호출자.** `44CEC0`(등장 상태 `CAppearArmyState` 갱신, UI 스레드: 목록 `+0x478`의 부대마다 `331780`이면 25DA10, 22ms 넘으면 `+0x480`으로 한 프레임 쉼)과 `2D53F0`(도적 생성)·`3A3960`·`4F8CF0`이다.
  - **불러오기 `508270` 3번 단계.** 불러오기 상태 갱신(UI 스레드, `572670` 확인)이 목록 `+0x490`의 부대 중 `2CB6C0(부대)==0`(자기 거점 칸 위가 아님)인 부대마다 슬롯 41을 부른다. 다른 검사는 없다. 4번 단계는 같은 방식으로 `11160()+0x28` 관리자를 채운다.
- **깃발이 떨어지는 때(원작 전부).** 관리자 `+0x150`을 부르는 곳은 `283ED0` 하나다. `283ED0`은 `2901A0`(삭제 대기열 `world+0x70`을 세계 뮤텍스 `world+8` 아래에서 처리)에서만 불린다. `2901A0`의 직접 호출자는 날짜 상태기계 case 0x1A(`44E723`)를 포함해 20곳이 넘는다(`9F860`, `2956A0`, `2A44C0`, `3A1630`…`3D8DA0` 등). `25A880`(부대 제거)은 대기열에 넣기만 하고, 이미 들어 있으면 바로 돌아간다.
- **결론.** 원작은 잃은 깃발을 다시 붙이는 경로가 없다. 저장 후 불러오면 `508270`이 본거지 밖 부대 전부에 깃발을 새로 붙인다. 그래서 "불러오면 깃발이 돌아온다"는 증상은 그 부대가 관리자 목록에서 빠졌다는 뜻이다(원인 미확정).
