## 1. 컨테이너 형식 (확정)

근거: `AI_TacticsMod/research/ui_atlas/build_layouts.py:6-22`(색인 해석), `research/speed_buttons/build_patch.py`의 `idrk_entry`(머리 필드·길이 0 조각·CRC), `docs/UI_ADD_GUIDE.md:84-86`, `docs/SPEED_AND_SAVE.md:17`(길이 0 조각 필수). 이번에 7개 rdb 전체를 독립 파서(`rdb.py`)로 다시 확인했다: 색인 항목 수와 헤더 수 일치, 본문 머리(전체/압축/원 크기·ktid·type)가 색인과 57,750개 모두 일치, 위치가 가리키는 뱅크 파일 범위 안.

### 1.1 색인 `<이름>.rdb` (`_DRK0000`)
- 헤더 0x20: `+0 "_DRK0000"`, `+8 u32 첫 항목 위치(=0x20)`, `+0xC u32 0x0a`(버전 추정), `+0x10 u32 항목 수`, `+0x14 u32 rdb 해시`, `+0x18 "data/"`(8바이트, 참조 폴더 접두).
- 이어서 `IDRK0000` 항목이 4바이트 정렬로 N개. 항목: `+8 u32 크기`, `+0x10 u64 위치문자열 길이`, `+0x18 u64 원(압축 해제) 크기`, `+0x20 u32 aux`, `+0x24 u32 ktid`, `+0x28 u32 type`, `+0x2C u16`, `+0x2E u16 kind16`(0x12 = 위치 있음, 0x11 = 위치 없는 참조, 0x01 = data 파일 참조 스텁), `+0x30 ...` 형식 매개 해시 열(`head_extra`, 3D 모델·텍스처에만 있음. 의미 추정: 하위 자원 형식 해시 목록), 맨 끝에 NUL 포함 위치 문자열.
- **위치 문자열** `"<오프셋hex>@<크기hex>[#<뱅크hex>[&<하위hex>]"`. 뱅크 b → 파일 `<이름>.rdb.bin` + (b 10진, 0이면 생략) + (하위 s가 있으면 `_s`). 예: `15becc7c@1c9c#e` → `system.rdb.bin14`; `6bd0000@3bd73#e&0` → `FieldEditor4.rdb.bin14_0`; `…#16` → `.bin22`.
- rdb의 마지막 항목(type `bf6b52c7`, kind 0x11, ktid = 헤더 해시)은 rdb 자신의 표지(확정, 크기 필드 의미는 미해결).

### 1.2 본문 `*.rdb.bin*` (항목 하나 = `IDRK0000` 머리 + 조각)
- 머리: `+8 u64 항목 전체 크기`, `+0x10 u64 압축부 크기`, `+0x18 u64 원 크기`, `+0x24 ktid`, `+0x28 type`, `+0x30 u32 압축부 CRC32`, 머리 길이 = 전체 − 압축부(0x38 + head_extra).
- 압축부: 원본을 16KB(16384)씩 끊어 각각 `u32 길이 + zlib` 이어 붙이고 **길이 0 조각으로 끝**(없으면 텍스처 로드가 끝나지 않음. 확정). 해제 후 크기 = 원 크기.
- 뱅크 파일은 최대 2GB(`ScreenLayout.rdb.bin`). 읽기는 mmap + 위치 탐색(`rdb.Archive.raw/read`).
- **색인이 가리키지 않는 뱅크 파일**(예비·이전 판 추정, 내용 비교는 두 건만 함): system `.bin2`; KIDS `.bin1/.bin6/.bin20/.bin21`; ScreenLayout `.bin27~.bin30`; FieldEditor4 `.bin2`; CharacterEditor `.bin2`(`.bin`과 앞 100MB 동일, 확정); MaterialEditor `.bin2`(`.bin`과 전체 동일, 확정); RRPreview `.bin2~.bin6`. 읽는 쪽은 색인 위치만 쓰면 되므로 무시해도 된다.

### 1.3 `0002/data/0x<ktid>.file` (확정)
단일 `IDRK0000` 항목 파일. **압축부 == 원 크기(원시 저장)**, 머리 0x38 뒤가 본문. 12개 모두 본문 `TSRS`(`KTSR` 소리 묶음) 또는 길이 0(`0x5c36aa53`) → 제외(소리), 목록만(`data_files.jsonl`). 색인 쪽 참조: RRPreview.rdb의 kind16=0x01 스텁(type `0d34474d` 8개, `a027e46b` 1개)이 가리킨다. 12개 중 3개는 어떤 rdb도 참조하지 않는다(미해결).

### 1.4 `0005/00N.bin` (확정)
`u32 N` + N×(`u32 오프셋`, `u32 크기`) 표 + 항목이 빈틈 없이 이어진다. 본편 000=300, 001=45, 002=300항목을 전수 검사했다. 항목은 `zp1` 압축 묶음(`+4 전체 크기, +8 조각 0x40000, +12 조각 수, +16 조각 저장 크기들, 0x800부터 0x80 정렬, 조각=u32(크기−4)+zlib`)이며 해제 결과는 `GT1G0600` BC3(fmt 0x5b) 텍스처다. 같은 zp1을 한국어 메시지에도 쓴다.

**얼굴 번호와 항목 계산 (현재 EXE 정적 분석):** 초기화 `42C0 → 8ACA70`은 종류 9·10·11 각각에 아래 구간을 등록한다. `8AA560`이 종류와 얼굴 번호로 등록을 고르고, `8ACF20 → 3E5F80`이 `종류별 그룹 × 구간 길이 + (얼굴 번호 − 구간 시작)`으로 해당 묶음의 항목을 읽는다. `85AE70 → 932DD0`은 종류 10의 작은 얼굴을 사용하는 경로다. 파일 구성·크기와 등록이 맞으며, 본편 000의 처음 두 얼굴은 세 그룹의 그림이 각각 같은 인물임을 직접 대조했다. 게임 내 표시 검증은 별도다.

본편 000~002는 215명, 645개 항목이다. 설치본 `DLC/0005/000~002.bin`은 본편 사본과 각각 SHA-256이 같으며, `DLC/0005/003.bin` 90항목도 같은 세 크기의 30개씩이다. 네 묶음의 735개 헤더 전부를 조회식의 번호·종류별 기대 크기 및 BC3 형식과 대조했다. 이 설치본의 본편 `0005`에는 003이 없다. 등록(`42C0`)에서 6000~6214의 세 묶음은 형식 3, 6215~6244(묶음 003)는 형식 2로 따로 등록된다. 파일 이름을 만드는 `8ABA60`은 묶음 표 `1A72310[번호×0x20]`의 첫 정수가 0이 아니면 `DLC/%s`를 앞에 붙인다(정적 분석, 2026-11-18). 그래서 003은 `DLC/0005/003.bin`에서만 읽힌다. 표의 그 값을 누가 채우는지와 DLC 가용 여부에 따른 실제 선택 조건은 미검증이다. 조회식은 `origlib.bin0005.portrait_location(face_id, kind)`에 구현했다. 2000번대 얼굴은 `texture_chara_center_`로 별도 등록되므로 6000번대와 구분한다. 언어 표지 없음 → 중립.

본편 `0010_KO`의 CE 시나리오 50개를 `origlib.scenario.scenario_ids/load_scenario`의 무장 `face` 필드로 전수 조회했을 때 6000~6244는 나오지 않았다. 별도로 설치된 `DLC/0010_KO` CE 시나리오 4개도 `origlib.dlc.load_dlc_scenario`와 시나리오 필드 명세로 조회한 결과 일치가 없었다. 따라서 이 54개 시나리오 표만으로 245명의 인물 이름은 확인할 수 없다. 다른 데이터나 게임 내 선택을 통한 사용 여부는 이 결과로 부정할 수 없다.

**그림 만들기 경로 (현재 EXE 정적 분석, 2026-11-18):** 첫 참조 때 `8ACF20(관리자, 그림 번호)`가 등록표 `1427D73F0`(0x140바이트 × 86칸, 그림 번호로 이분 탐색)에서 형식을 고른다. 형식 2·3(0005 묶음)은 `3E5F80(묶음 핸들, 항목 순번, 0)`이 zp1 항목 바이트를 새 메모리로 읽고 `8AD530(관리자, zp1, 그림 번호, p4)`가 `30B840`(풀린 크기)·`30AB30`(풀기)·`953AB0`(GT1G → 텍스처)으로 텍스처를 만들어 `관리자+0x178[번호]`에 둔 뒤 호출자가 zp1을 `_free_base`한다. 형식 1은 이름으로 `3E6240`을 읽어 같은 `8AD530`을 부르고, 그 밖은 `8AA700` 경로 + 작업(`B3BB50`, `14CF0` 대기) → `8AA020`이다. `8AD530`의 호출자는 `8ACF20` 두 곳(`8AD01B`, `8AD16C`)뿐이다. `8AD530`은 성공하면 1(텍스처 객체를 `관리자+0x178`이 가리키는 포인터 배열 [그림 번호]에 둠), `953AB0`이 거절하면 0을 돌려주며 `30AB30`의 풀기 결과는 보지 않는다. **zp1 조각 풀기 규칙(`30AB30`, 2026-11-19 기계어 확인)**: 크기 칸 = 머리 +4(`30B840`), 조각 크기 +8, 조각 수 +0xC, 조각별 크기 +0x10[]; 조각은 0x800부터 0x80 정렬. 마지막이 아닌 조각은 크기 칸이 조각 크기 이상이면 **압축 없는 원본으로 그 조각 크기만큼 복사**(`30AC72`: `mov r8d,esi` → memcpy)하고, 작으면 u32 길이 + zlib으로 푼다. 마지막 조각(크기 = 전체 % 조각 크기, 0이면 조각 크기)은 머리 +3 바이트의 비트 2가 켜져 있으면 복사, 아니면 zlib. 얼굴 항목 GT1G 머리는 세 크기 모두 56바이트(`+8` 파일 크기, `+0xC` 0x20, `+0x10` 1장, `+0x14` 0x0A, `+0x20` 4, `+0x24` 텍스처 머리 20바이트: 밉 1, 형식 0x5B, `+0x26` = log2 가로 | log2 세로 << 4)이고 그 뒤가 BC3 본문(가로×세로 바이트)이다(origlib `bin0005`로 얼굴 6214 세 항목 대조). 깃발 얼굴은 `1BA4E0 → 932D40 → 932DD0`(얼굴 종류 10)으로 위 가용성 검사를 지난다. 근거 `decomp_cache 8ACF20,8AD530,8AA560,1BA4E0,932D40`, `ghidra_full callers 8AD530`. 게임 내 검증은 별도.

**표시 전 가용성 검사:** `932DD0`은 `370FB0`이 참인 얼굴에 `3712A0 → 370670`의 두 비트 집합을 검사해 하나라도 실패하면 얼굴 2000으로 대체한다. `370FB0` 기준 6000~6214는 이 검사 대상에서 제외되고, 6215~6244는 대상이다. 별도로 종류 9~12의 특정 얼굴 구간은 `8ACC10`으로 관련 묶음의 가용성을 확인하고 실패 시 역시 2000으로 바꾼다. 이 분기와 비트 검사는 정적 분석으로 확정했으나, 비트를 어떤 DLC·소유권 조건이 채우는지는 아직 확인하지 않았다. `portrait_location`은 순수 인덱스 변환이므로 이 가용성 판정을 수행하지 않는다.

비트 집합의 한 입력 경로는 `3721C0 → 371DB0 → 371A10`이다. `3721C0`은 `DLCInfo`가 들어간 항목을 찾고, `371DB0`은 내용을 세 정수의 쉼표 구분 행으로 파싱한다. `371A10`의 종류 3은 얼굴 번호가 `370FB0` 대상이면 첫 비트를 설정하고, 세 번째 정수가 19보다 작을 때 두 번째 비트도 설정한다. 이 코드만으로 세 번째 정수의 업무상 의미나 모든 입력 경로를 확정하지 않는다.

이 입력 경로는 `3721C0`에서 Steam 인터페이스의 두 결과를 검사해 둘 다 참일 때 읽기로 들어간다. `371720`의 읽기 후 `3729D0`이 상태 `state = state × 0x6C078965 + 0x3039 (mod 2^32)`를 바이트마다 먼저 갱신하고 상태의 상위 두 바이트를 XOR한다. 상태 초기값은 해당 경로에서 확인한 정수와 파일 이름의 숫자를 더해 만든다. 이는 실행 파일의 정적 경로를 기록한 것으로, 소유권 판정 결과나 설치된 DLCInfo의 해독 결과를 주장하지 않는다.

## 2. ktid·type의 의미
- `type`: 자료 종류를 가리키는 32비트 해시(해시 함수 미해결). 같은 type의 본문 머리는 항상 같은 형식 → 아래 3절 표로 고정(확정).
- `ktid`: 항목 식별자(32비트, 이름/경로 해시로 추정). 한 rdb 안에서 본문 항목 ktid 중복 없음(확정). 스프라이트 표와 텍스처의 짝(8,476 대 8,476)은 ktid로 연결되지 않는다(교집합 0, 인접 쌍 3,976; 연결 규칙 미해결).

## 4. 언어 처리 (사용자 2026-11-07: KO만)
rdb·0005에는 언어별 폴더가 없고, 언어 표지는 **이름 안의 접두/접미 토큰**(`kr_`·`en_`·`jp_`·`ch_`·`cn_`·`tw_`)으로만 나타난다. 이 토큰이 있는 것은 스프라이트 표(이름 목록)와 LCSK 레이아웃(이름 표)뿐이다. 판정 `rdb.lang_class()`: 토큰 없음=중립 / KO만=ko / KO+타언어=mixed / 타언어만=foreign.
- 스프라이트 표 8,476: 중립 5,541, **ko 577**, foreign 2,358(en 538·jp 408·ch 783·tw 632·cn 360개 표에 등장, 겹침 있음). LCSK 1,085: 중립 1,000, foreign 84, mixed 1.
- 해독 내용(`sprites_ko.jsonl`)에는 중립·ko·mixed 표 6,118개만 담고, foreign 2,358은 목록(`ScreenLayout.jsonl`의 `lang`)에만 있다. 텍스처(G1T)·모델·셰이더 등은 언어 표지가 없어 모두 `neutral`(텍스처가 어느 언어 화면에 쓰이는지는 표↔텍스처 연결 미해결이라 구분 못 함, 미해결).
- `ch_`가 번체/간체 중 무엇인지는 `ch_..._cn` 같은 이름이 있어 불명(미해결, 어차피 foreign으로 취급).

## 5. 해독된 구조

### 5.1 스프라이트 표 `f20de437` (확정)
`u32 개수 c` + c×104바이트: `이름[64]`, `u32 쪽(텍스처 쪽 번호)`, `float uv 8개(좌하/우하/좌상/우상 순서 4점 x,y)`, `u32 1`. 크기 = 4+104c(전수 일치). 예: `face_0736_ctr`(초상 중심). 근거: `speed_buttons/build_patch.py`의 `meta_entry`와 일치.

**초상화 표와 텍스처의 짝(2026-11-17, ScreenLayout 전수 + 그림 확인)**: 묶음 파일 안에서 `[G1T 텍스처][그 텍스처의 스프라이트 표]` 순서로 빈틈 없이 이어진다(`텍스처 위치 + 저장 크기 == 표 위치`). 얼굴 번호 N(무장 `+0xA6` 얼굴 번호 = 세이브 `+0xAC`)의 흉상은 표 안의 `face_NNNN_ctr` 칸이고, 그 칸의 쪽 번호가 바로 앞 G1T의 쪽이다. 대부분은 512×512 BC3 한 쪽 + 한 칸짜리 표(uv 0~0.945 × 0~1 = 484×512)이고, 나이별 그림이 있는 얼굴은 5쪽 텍스처 + 2칸 표(`face_NNNN_ctr`, `face_NNNN_unique`)다. 머리 영역은 (64,0)-(448,384). 표 뒤의 텍스처를 고르면 한 칸씩 밀린다(얼굴 2 = 관우, 1 = 장비로 그림 확인). 같은 번호의 `face_NNNN_a/b/c`(2048×1024, 전신 3종)와 `face_NNNN_unique`(1024×1024)는 따로 있다. 나이 얼굴 19개(2179~2197)는 자기 번호로 된 칸이 없고, 바탕 얼굴 번호에 `b`를 붙인 `face_NNNNb_ctr`·`face_NNNNb_a/b/c`·`face_NNNNb_unique`로 들어 있다(예: 2184 = `face_0064b_ctr`, 아래 5.1.1).
- 짝 규칙 보충(2026-11-17 전수): `.bin22`는 항목을 16바이트로 맞춰 텍스처 끝과 표 사이에 0~15바이트 틈이 있다(얼굴 2500~2509·3000~3005). 틈을 허용하면 짝으로 찾는 얼굴이 1,453 → 1,468장. `face_NNNN_ctr` 칸은 아카이브 전체에 1,470개다. 나머지 둘(992·5012)은 표 바로 앞이 색인에 없는 옛 저장본이다(2026-11-18 해결): 표 앞 빈자리에 저장 머리 `IDRK0000`(`+8` 전체 크기, `+0x18` 풀린 크기, `+0x24` ktid, `+0x28` type)가 있는 G1T가 놓여 있고, 같은 ktid의 텍스처는 색인에서 다른 묶음 위치를 가리킨다. 5012: 표 bin5 `0x1199980`, 숨은 머리 `0x1180d1b`, ktid `0xddb08b7e`, 색인 위치 `1288390@18c57#6`. 992: 표 bin14 `0x243fa31`, 숨은 머리 `0x2422228`, ktid `0x12bf2a18`, 색인 위치 `f725@1e316#11`. 두 경우 모두 숨은 머리의 전체 크기가 빈자리보다 작고 차이는 16바이트 미만이다. 색인 쪽 텍스처를 쓰면 992는 다른 얼굴과 같은 512×512 BC3 흉상으로 풀린다(그림 확인, 5012는 그림 미확인). 원작이 이 짝을 실행 중에 어떻게 찾는지(ktid 조회인지)는 확인하지 않았다.
- 세이브 무장 얼굴 번호(`+0xAC`)에는 시나리오에 없는 2000번대가 나온다: 손권 2184(시나리오 얼굴 64)·순욱 2189·여몽 2181(`autosdexceKO01`, 무장 1,400명 중 ScreenLayout에 없는 얼굴은 이 셋과 992뿐). **2026-11-18 해결**: 이 번호들은 나이 얼굴이며 그림은 바탕 얼굴 이름의 `b` 칸에 있다(5.1.1). 0005를 이 번호의 후보로 보았던 이전 추정은 철회된 그대로다. 읽는 코드: `AI_TacticsMod/tools/bond_calc/extract.py`의 `face_index`·`face_png`(이 도구는 `b` 칸을 아직 읽지 않는다).

#### 5.1.1 나이 얼굴 그림 이름 (현재 EXE 정적 분석, 2026-11-18)
- 스프라이트 이름은 `8AE2D0`(`face_%04d_ctr`/`face_%04db_ctr`), `8AE230`(`face_%04d_%s`/`face_%04db_%s`, 전신 a·b·c), `8AE330`(`unique`)이 만든다. 셋 다 먼저 `2AB9F0(얼굴, 0)`으로 나이 얼굴 표(`1A25E20`, 19행)에서 바탕 얼굴을 찾는다. 결과가 입력과 같으면 `face_%04d_…`, 다르면(나이 얼굴) **바탕 번호**로 `face_%04db_…`를 만든다. 예: 2184 → `face_0064b_ctr`.

### 5.2 KIDS DOK `20a6a0bb` (구조 확정, 속성 의미 추정)
헤더 28바이트: `"_DOK0000"`, `u32 0x1c`, `u32 0x0a`, `u32 객체 수`, `u32 해시`, `u32 전체 크기`. 이어서 `IDOK0000` 객체가 **4바이트 정렬**로 이어진다: `+8 u32 크기`, `+0xC u32 객체ID`, `+0x10 u32 클래스 해시`, 그 뒤 속성(12바이트 3열 `(종류 u32, 값 u32, 이름해시 u32)`과 길이 접두 문자열이 섞임, 추정). 4,543개 DOK의 객체 수가 헤더와 일치, 24개(28~140바이트)는 객체 없이 다른 꼬리만 있다(미해결). 내용: 문자열 전수 집계(4,880종)에서 `kids::math::…`, `kids::pose::…`, `mud::from_kidshost::…`, `kids::dbg::Trace` 같은 **엔진 스크립트 함수 이름**과 렌즈·그림자 같은 렌더 설정만 나왔고 게임 규칙 용어는 없었다(확정).
원작 UI의 `common setting` 객체 ID `61AD16CF`는 `KIDSSystemResource` 아카이브의 DOK `6D011726` 내부에 있다. 이 객체의 속성 서술자는 `(형식, 원소 수, 키)` 12바이트씩이고 본문은 서술자 순서로 이어진다. 이 객체에서 형식 1은 바이트, 5는 u32이며 23개 속성을 소비하면 객체 경계와 정확히 일치한다. 레이아웃 이름 해시 열 `10FA95C2`와 객체 열 `B45B5E75/1BF404E7`은 각각 1,085개다. 두 객체 열은 DOK `208BE13A`를 거쳐 동일한 LCSK KTID 전부로 이어진다. ### 5.3 LCSK
머리 `LCSK<버전4자리>`, `+8 전체 크기`, `섹션 1 +0x12 u16 노드 수`, 섹션은 `0x4c`부터 `(종류,크기)` 연속. 부품·이름 표의 근거는 `AI_TacticsMod/research/ui_atlas/build_layouts.py`와 `layout_bodies/`다. 구형 8400의 부모/자식 수 오프셋과 8500 세 파일의 자식 수 차이는 [UI 2.3절](ui_native.md)에서 설치본 본문과 대조했다.

### 5.4 G1T
