# 대도서관 규칙

## 원작 사실을 공동으로 축적한다

`docs/orig/`에는 원작의 데이터 형식·함수·구조체·규칙·UI·AI 동작만 둔다. 특정 모드의 변경 목표, 기능 설정, 설치 이력은 그 모드 저장소에서 관리한다. 공통 호환 규약은 별도 문서로 둔다. 원작 사실과 모드의 개선안을 섞지 않는다.

## 먼저 찾고 기존 절을 보완한다

분야 목차 → 해당 문서 → 원작 데이터 리더 → 로컬 캐시 순서다. 조사 회차별 문서를 계속 늘리지 않는다. 구조체 필드 뜻·함수 식별자는 Markdown와 JSON 색인이 서로 맞게 수정한다. 기존 결론을 뒤집으면 본문을 수정하고 같은 문서의 정정 기록에 이전 해석·정정 이유를 남긴다.

## 근거 단위로 확신도를 쓴다

- **확정**: 주장을 뒷받침하는 바이트·원작 호출자·데이터 교차 확인·실측 등 근거와 범위가 분명하다.
- **추정**: 의사코드 해석, 이름 유사성, 표본·패턴 또는 불완전한 증거에 의존한다.
- **미해결**: 결론이 없고 다음에 필요한 증거가 명시되어 있다.

"확정"도 빌드·상황·관찰 범위 안에서의 표현이다. 정적 분석으로 확정한 분기가 실제 게임 시나리오에서 검증되었다는 뜻은 아니다. 문서의 조사 상태를 일괄적으로 상향하지 않는다.

기여하는 사실에는 Steam buildid와 분석 EXE 전체 SHA256, 함수 RVA 또는 데이터 파일·오프셋, 확인 방법, 확신도, 미확인 범위를 단다. 다른 빌드는 별도 표에 대응 관계와 근거를 적는다. 서로 다른 빌드 주소를 같은 함수라고 자동 연결하지 않는다.

## 디컴파일은 개발사 소스가 아니다

의사코드는 기계어를 해석한 결과다. 함수 이름·서명·형식은 틀릴 수 있다. 훅과 원작 함수 호출에는 원래 바이트·호출자·ABI·인수 모양·소유 스레드·공유 작업 공간 확인이 필요하다. 자동 색인·fixture·빌드 성공은 개별 함수의 의미나 실게임 안정성을 입증하지 않는다.

## 기여는 PR과 유지관리자 검토로 받는다

중복 조사 방지를 위해 큰 조사 전에는 기존 Issue를 찾고 조사 범위를 알린다. 같은 주제를 누가 조사 중인지 확인한다. 자동 검사는 형식과 회귀를, 유지관리자 검토는 주장의 근거와 기존 설명의 일관성을 맡는다. AI가 작성한 PR도 같은 기준이다. 게임 파일·전체 코드 덤프를 제출하지 않는다.
