# AI와 모더를 위한 모드 호환 규약

## 목적과 범위

각자 모드를 만들면서 훅·설치 파일·설정·UI·저장 자료의 충돌을 미리 드러내고, 향후 모드 매니저가 의존성과 설치·제거 순서를 판단할 수 있게 한다. 이 문서는 기존 AI교정 모드의 모듈 매니페스트와 호환 지침에서 공통 원칙을 추렸다. **범용 모드 매니저와 외부 안정 ABI가 완성되었다는 뜻은 아니다.**

현재 제공하는 공통 매니페스트는 `schema: 1`이다. 기존 AI교정 모드 내부 `module.json`과는 별도 외부 패키지 형식이며 자동 호환한다고 가정하지 않는다. 공통 도구는 선언된 충돌을 정적으로 검사한다. 누락된 훅, 행동 의미·실행 순서·동시성 충돌은 별도 검토와 실게임 확인이 필요하다.

## 대도서관을 사용하면 어디까지 알 수 있나?

**원작의 호출 흐름과 입출력을 공유하고 각 모드가 바꾸는 범위를 명시하면, 같은 자리를 다시 조사하지 않고 충돌과 체인 순서를 검토하기 쉬워진다.** 다만 대도서관은 모든 모드의 변경을 자동으로 관찰하거나 훅을 연결하는 실행기가 아니다.

| 자료 | 알려 주는 것 | 별도로 확인할 것 |
|---|---|---|
| 원작 문서·로컬 캐시 | 조사된 함수의 의미, 호출자·호출 대상, 구조체와 데이터 위치 | 대상 빌드에서 입출력·부수 효과·ABI가 그 해석과 맞는지 |
| 모드의 변경 설명·훅 계약 | 그 모드가 어느 호출·입력·결과·상태를 언제 바꾸는지 | 해당 **버전의 실제 소스와 훅 등록**이 선언과 일치하는지 |
| 매니페스트와 정적 검사 | 선언된 훅 범위·파일·설정·UI·자원·의존성의 중복 | 선언 누락, 의미상 충돌, 체인 ABI·순서·동시성·해제 안전성 |
| 조합별 실게임 검사 | 특정 버전·설정·실행 순서에서 관찰한 동작 | 미실행 조합, 다른 패치, 장시간 실행 등 미확인 범위 |

다른 모드가 변경 정보를 제공하지 않으면 문서만으로 그 모드가 어디까지 건드렸는지 알 수 없다. 함수·구조체 색인은 전부 검증된 API 명세가 아니며, 호출관계 표도 간접 호출·동적 디스패치의 모든 대상을 보장하지 않는다. 모르는 항목은 미확인으로 남긴다.

## 모드마다 선언할 것

`examples/example-mod.json`과 `schemas/mod-manifest.schema.json`을 따른다.

- 전역에서 구별되는 `id`(예: `author.mod-name`), 버전, 대상 EXE와 분석 SHA256.
- `depends`: 필수 패키지 id. 버전 범위는 현 규격에서 자동 해석하지 않으므로 별도 notes로 명시한다. `conflicts`: 함께 쓸 수 없는 패키지 id.
- `hooks`: 종류(code/call/vtable), **현재 빌드 RVA**, 실제 교체 길이, 원래 바이트·값을 확인하는 guard의 근거, 불일치 시 해당 기능 중단 정책. vtable은 실제 슬롯의 RVA와 길이 8을 적는다. 함수 시작 주소만 적고 패치 자리를 생략하지 않는다.
- `files`: 게임 설치 폴더 기준 상대 파일 경로. 경로의 대소문자·슬래시 차이는 같은 파일로 본다. EXE·세이브·백업 소유 선언은 금지한다.
- `settings`: 설정 파일, 섹션, 키. `ui`: `author.mod:entry`처럼 구별되는 화면 소유 id. `resources`: 실제 공유 파일·bank·레코드 id를 합친 표준화된 소유 키. 예를 들어 `0002/screenlayout.rdb:bank:24`로 적으며 모더 이름을 붙여 같은 자원의 충돌을 숨기지 않는다. 전체 파일을 독점 교체하면 `files`에도 그 파일을 선언한다.
- `provides`·`uses`: 제공·사용 API 이름. 버전은 이름에 넣는다(예: `author.mod.api/v1`). 안정성·등록 시점·스레드·콜백 수명은 해당 API 계약에 적는다.
- `off_behavior`·`uninstall`·`notes`: 기능 OFF, DLL 부재, 제거와 복원, 검증된 조합과 미확인 범위.

## 훅 소유와 체인

한 패치 자리에는 조정된 소유자 하나를 둔다. 원래 바이트 또는 vtable 값이 다르면 무조건 덮어쓰지 않고 해당 기능을 끈다. 체인은 양측이 허용한 자리에서만 합의하고 현재 "다음" 함수를 보존해 호출한다. 자기 훅·원작 주소를 반복 호출하는 순환을 막는다. 선언만 같다고 체인이 안전하다고 판정하지 않는다.

실제 변경 구간이 겹치면 오류다. 서로 다른 패치라도 같은 16바이트 블록을 건드리면 원자 교체 충돌 가능성을 경고한다. 패치가 여러 블록을 걸칠 때도 전체 길이를 비교한다. 서로 다른 빌드의 RVA를 직접 비교하지 않는다.

### 모드가 공개해야 할 호출·입출력 변경 범위

모드 저장소에 [훅 계약 템플릿](../examples/HOOK_CONTRACT.md)을 복사해 기능·훅별로 작성하고, 매니페스트 `notes` 등에서 그 문서 위치를 안내한다. 원작 사실은 대도서관에, 해당 모드의 변경 계약은 그 모드 저장소에 둔다. 여러 모드의 같은 계약 이름이 실제 호환을 뜻하지 않으므로 모드 id·버전·commit과 대상 게임 해시를 함께 기록한다.

| 항목 | 기록할 내용 |
|---|---|
| 정확한 지점 | 원작 함수 시작 RVA, 실제 패치 RVA·길이·종류, 호출 지점 또는 vtable 슬롯과 적용 객체 범위, 원래 바이트/값 가드의 근거 |
| 원작의 호출 조건 | 누가 언제 부르는지, 게임 UI/AI 등 소유 스레드, 허용한 호출 경로와 인수 형태, 확인한 호출자 |
| 입력 | `this`와 객체 수명, 각 인수의 뜻·폭·단위·유효 범위·플래그, 포인터의 읽기/쓰기와 버퍼 길이·소유권 |
| 출력과 부수 효과 | 반환값의 뜻·범위·실패 표현, 출력 인수·참조 버퍼, 함수가 바꾸는 구조체 필드·공유 상태·자원 |
| 모드의 변경 | 원작/다음 함수를 부르기 전 바꾸는 입력, 호출 후 바꾸는 반환값·출력·상태, 적용 조건과 제외 대상 |
| 호출 횟수·수명 | 원작/다음 호출을 생략·반복하는 경로, 이벤트·콜백 등록, 공유 임시 버퍼, 재진입 가능성과 유효 기간 |
| 체인·해제 계약 | 다음 함수의 획득 경로, ABI, 조정 주체, 허용한 순서와 조합, OFF·제거 때 되돌릴 범위와 실행 중 호출 처리 |
| 근거와 검증 | 원작 호출자/바이트/명세의 근거, 확신도, 상대 모드의 정확한 버전·설정·순서, 실행한 검사와 미확인 |

원작 함수를 직접 호출하는 기능도 대상 함수·호출 시점·인수·부수 효과를 기록한다. 직접 패치하지 않는다고 행동 충돌까지 없는 것은 아니다. 같은 값이나 게임 명령을 서로 다른 훅에서 바꾸는 경우도 변경 범위에 포함한다. 이 표는 조사·설계를 위한 계약이며, 외부 프로세스 메모리 쓰기나 임의 스레드에서의 원작 호출을 허용하지 않는다.

### 체이닝 전에 합의할 것

체인은 각 모드가 같은 자리를 순서 없이 덮어쓰는 방식으로 만들지 않는다. 현재 등록된 다음 함수 포인터나 조정자가 제공한 다음 호출을 사용하고, 원작 주소를 고정 호출해 앞선 모드를 우회하지 않는다. 알 수 없는 detour의 점프 목적지를 보고 함수 형식과 체인 가능 여부를 추측하지 않는다.

1. **호출 규약 확인**: 모든 참여자의 실제 ABI, 인수·포인터·반환 규약과 객체 수명이 맞아야 한다. 디컴파일러가 표시한 서명만으로 형식을 확정하지 않는다. 원작 호출자·바이트와 필요한 명령어 근거를 확인한다. 서로 다른 빌드는 별도 검증한다.
2. **다음 호출 규칙 명시**: 기본은 다음 함수를 한 번 호출하는 형태로 설계하되, 원작을 생략하거나 여러 번 호출하는 기능은 그 경로와 영향부터 합의한다. 원작이 해야 할 정리·등록·상태 변경이 누락되거나 중복되지 않는지 확인한다.
3. **순서·반환값 합의**: 누가 입력을 먼저 바꾸고, 누가 최종 결과를 결정하는지 정한다. 다른 모드가 만든 결과를 원작 값으로 다시 덮어쓰는지, 오류·예외·거부 시 어느 결과를 전달하는지도 기록한다.
4. **상태와 실행 맥락 확인**: 게임 소유 스레드, 중첩 호출·재진입·공유 작업 공간, 출력 버퍼의 유효 기간을 맞춘다. 입력과 반환값이 같아도 내부 상태 변경은 서로 충돌할 수 있다.
5. **등록·해제 조정**: 체인을 관리하는 주체를 정한다. 체인 중간의 모드를 끄면서 슬롯을 원작으로 통째로 되돌리면 다른 모드까지 끊길 수 있다. 남은 모드가 제거한 DLL의 함수나 이미 해제된 UI·버퍼를 참조하지 않도록 등록 해제·연결 재구성·실행 중 호출의 종료를 조정한다. 안전한 해제가 구현·검증되지 않았으면 실행 중 DLL 제거를 지원한다고 선언하지 않는다.

다음은 **실제 게임 식이 아닌 순서 설명용 예시**다. 원작 결과가 100이고 A는 결과에 10을 더하며 B는 결과를 2배로 만든다고 하자.

```text
게임 → B 전처리 → A 전처리 → 원작 → A 후처리 → B 후처리
결과: (100 + 10) × 2 = 220

게임 → A 전처리 → B 전처리 → 원작 → B 후처리 → A 후처리
결과: (100 × 2) + 10 = 210
```

두 모드가 같은 서명을 쓰고 모두 다음 함수를 한 번 호출하더라도 순서에 따라 결과가 달라진다. 한 모드가 다음 호출을 생략하면 뒤쪽 모드와 원작이 아예 실행되지 않을 수 있다. 따라서 "체인에 연결됨"과 "의도한 게임 동작이 함께 유지됨"을 나눠 검증한다.

### 모드 제작 AI가 제출할 호환성 보고

구현 전에는 관련 원작 문서·호출자·입출력을 찾고, 자신의 훅 계약과 상대 모드의 현재 선언을 비교한다. 구현 후에는 실제 등록 지점과 변경 범위가 선언에 맞는지 다시 검토한다. 상대 자료가 없으면 "미확인"으로 보고한다.

보고에는 다음 네 가지를 구분한다.

- **선언상 충돌 없음**: 확보한 선언에 대한 정적 검사 결과. 실게임 호환 판정이 아니다.
- **충돌 발견**: 실제 자리·파일·상태·순서의 충돌 내용과 조정 방법. 같은 훅의 체인 합의만으로 정적 오류를 지우지 않는다.
- **체인 계약 검토**: 확인한 ABI·입출력·호출 횟수·순서·수명과 아직 확인하지 못한 부분.
- **실게임에서 확인한 조합**: 모드 버전·게임 해시·설정·설치/등록 순서, 단독·동시 활성화·한쪽 OFF·저장/불러오기·화면 종료 등 해당 변경에 필요한 실제 확인 범위.

주소가 다르더라도 같은 게임 상태나 명령을 변경하면 의미상 충돌이 있을 수 있다. 정적 검사가 통과한 뒤에도 이 범위의 검토가 필요하다.

## 파일·자원·설정·저장

프록시 DLL 이름이 겹치면 설치 순서와 체인·업데이트·제거 규칙을 명시한다. 다른 모드 DLL을 허락 없이 덮어쓰지 않는다. 원본 EXE는 보존한다. UI 아카이브·bank는 변경한 레코드와 자신이 만든 자원만 추적하고, 공유 파일 전체 덮어쓰기와 무조건 원복을 피한다.

다른 모드의 설정 파일·키·로그 이름을 사용하지 않는다. 원작 세이브 형식을 바꾸지 않고 필요 자료는 모드 id·스키마 버전이 있는 별도 sidecar로 관리하는 것을 권장한다. 설치·갱신·제거는 파일 해시와 소유 기록을 확인하고, 다른 프로그램이 수정했으면 멈추고 보고한다. 기존 사용자 파일·백업을 보호한다.

게임 효과는 게임 UI/AI 스레드의 원작 함수 호출 또는 훅으로 만든다. 외부 프로세스 메모리 쓰기·원격 호출을 사용하지 않는다. 기능 OFF·모듈 부재·제거 시 그 기능의 UI·구독·자원을 해제하고 원작 또는 앞서 설치된 모드의 동작으로 돌아가야 한다.

## 정적 충돌 검사

```powershell
.\library.ps1 compat .\examples\example-mod.json .\examples\another-mod.json --json
```

패키지 id·대상 빌드·의존성·순환·명시 충돌·API·설치 파일·설정 키·UI·자원 키·훅 범위·16바이트 블록을 비교한다. exit 0은 선언된 오류가 없다는 뜻이고, 경고는 남을 수 있다. exit 1은 충돌, exit 2는 형식 오류다. 정적 검사 통과를 실게임 호환 보증으로 표시하지 않는다.

**현재 검사는 함수 입출력·ABI·부수 효과·체인 순서를 분석하지 않으며, 자동 체이닝 기능도 없다.** 훅 계약 문서나 `notes`에 체인 합의를 적어도 실제 훅 구간이 겹치면 계속 오류로 보고한다. 그 문서를 읽고 코드를 검토해 조정해야 한다. 예를 들어 실제 패치 소유자를 한 조정자로 모으고 참여 모드는 해당 API에 등록하도록 구현했다면, 매니페스트도 그 실제 소유 관계를 반영한다. 충돌을 숨기려고 실제 패치 선언을 지우지 않는다. 이번 안내는 새 런타임 API나 체인 검사 기능을 추가한 것이 아니다.

## 기존 AI교정 모드와 함께 쓸 때

[AI교정 모드의 호환 지침](https://github.com/t3ferii/san14ce-ai-mod/blob/main/docs/MODDER_COMPAT.md)을 해당 버전 소스와 함께 확인한다. 이 도서관은 그 모드의 최신 설치 상태나 모든 훅을 자동 추적하지 않는다. 현재 버전의 실제 선언을 확보하기 전에는 "호환 확인"으로 표시하지 않는다.

기존 로더의 `dinput8.dll` 자리, 같은 훅·vtable 슬롯과 16바이트 블록, UI `ScreenLayout.rdb`와 모드용 bank를 확인한다. 기존 문서 기준 bank 24~31은 해당 모드가 쓰므로 조정 없이 사용하지 않는다. `SAN14_Layout.dll` API는 외부 모드용 안정 ABI 검증 사례가 아직 없다는 기존 문서의 한계를 유지한다.

우리 프로젝트 내부의 DLL 구성·단일 설정 파일·로깅·설치기 카탈로그 규칙은 그 프로젝트를 수정할 때 적용한다. 독립 모드에 같은 DLL 수나 같은 설정 파일을 강제하지 않는다.
